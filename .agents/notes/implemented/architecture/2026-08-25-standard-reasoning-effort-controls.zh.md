# Agent Note: 标准推理档位控件

Status: implemented

[English](2026-08-25-standard-reasoning-effort-controls.md) | 中文

## 问题

提供方与模型 catalog 对推理元数据的声明并不一致，许多网关列表完全省略该字段，私有路由也可能以 catalog 无法识别的 owner 暴露可用模型。若用这些声明决定输入框是否显示控件，同一会话行为就会依赖 catalog 新鲜度与提供方归属，还会在端点应用自身兼容行为之前阻断尽力请求。

## 决策

`LlmRuntime` 会把适配器推理元数据替换为每条已解析路由统一的四档：`off`、`low`、`high`、`max`。输入框在前面附加 `Default`；它不会存储显式 `reasoningEffort`，切换模型也会回到 `Default`。核心校验只接受四个显式标准 id，不会把适配器默认值实体化到会话选择中。

`llm-pi-ai` 对 Default 调用保留原始模型描述符。显式选择会创建分离的请求描述符并启用推理，保留已配置的 `thinkingLevelMap` 协议拼写；没有映射时，`max` 使用同名规范值。pi-ai 继续持有协议翻译，包括各协议特有的 Off 行为。提供方若未实现所选档位，会返回自己的常规请求错误；模型发现与 `dsh-model-catalog` 不会隐藏控件。

原生 DeepSeek 已经序列化同样的四个显式档位。`reasoningEfforts` 继续作为私有网关协议映射配置，而不是选择器能力声明；路由级 `reasoning` 继续作为会话选择 Default 时使用的部署行为。

## 曾考虑的替代方案

**保留适配器持有的逐模型菜单。** 未采用：缺失、陈旧、歧义或网关特有的声明会改变 UI 可用性，并在提供方 I/O 前拒绝请求。

**显示全部 pi-ai 档位。** 未采用：`minimal`、`medium`、`xhigh` 会让公共菜单再次依赖提供方。四档集合与原生 DeepSeek 协议一致，也符合跨提供方统一控件的需求。

**发送合成默认档位。** 未采用：Default 表示没有会话级覆盖。实体化某个档位会替换提供方或部署策略，并让模型切换携带隐藏行为。

## 后果

- 每个已公布模型都精确显示 `Default`、`Off`、`Low`、`High`、`Max`，不依赖提供方、owner 或云端声明。
- 不支持的显式档位会在提供方处失败，而不是从 UI 消失或在能力预检中失败。
- `dsh-model-catalog` 只负责输入模态，不解析或发布推理控件。
- 仅当用户显式选择标准档位时，会话日志才保留该值；回放会复现可见选择，Default 则保留提供方行为。
