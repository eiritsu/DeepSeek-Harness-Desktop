# Agent Note: A macOS shell for the complete Web profile

Status: implemented

English | [中文](2026-08-23-macos-desktop-shell.zh.md)

## Problem

The shipped `dsh web` application requires a browser even though it binds only to loopback. A local desktop install needs native window and lifecycle behavior without forking the Web client or removing the plugin composition, sandbox policy, approvals, settings, and persistence that the Web profile already owns. Source releases also change faster than a signed desktop bundle should need to change.

Executing a source update in place is unsafe. A dependency or build failure can leave no runnable version, local changes can conflict with upstream, and an application cannot prove readiness by treating a successful Git command as a working runtime.

## Decision

`desktop-shell/` is a macOS 13 Swift application that starts the built CLI with `web --no-open --port 0` and embeds the announced loopback URL in WKWebView after that address returns HTTP 200. Runtime stderr remains diagnostic log output and cannot replace startup presentation; stdout progress stops when the readiness line is accepted. Each random port creates a distinct Web origin, so a document-start script restores the browser's `dsh.sessions.current` cell from native preferences and mirrors later changes through a main-frame, loopback-only WebKit message handler. The bridge carries only the opaque current-session selection record; session logs, drafts, settings, and plugin state keep their existing owners. The official Web profile remains the application; the native code owns only process lifecycle, navigation to the local address, this cross-origin selection continuity, source selection, plugin command orchestration, and desktop presentation. A native Edit menu sends standard undo, redo, cut, copy, paste, and select-all actions through the AppKit responder chain, allowing the focused WKWebView control to handle the corresponding Command shortcuts. The full-size transparent title bar keeps the Web presentation visually integrated. Because WKWebView does not claim window movement, a native drag view covers only the title-bar-height blank area to the right of the sidebar and is disabled in full screen.

Application Support owns one persistent `DSH_HOME` for sessions, settings, credentials, profiles, and plugins. Source versions live separately. Plugin menu commands stop the visible runtime when they mutate the Web profile, invoke the official `dsh plugin --profile web` entry with the repository-pinned pnpm version available on `PATH`, and restart the same source version. The shell therefore preserves bundle reconciliation instead of editing profile dependencies itself.

A startup failure that names one Bundle package is eligible for automatic recovery only when that package is an out-of-tree dependency enabled by the Web profile. The shell creates a temporary profile that preserves the Web profile's configuration and every other Bundle, links to the same installed dependency tree, omits the failing Bundle, and retries once. It does not edit the Web profile or uninstall the package, and it removes the temporary profile after the recovered runtime stops. The next application launch therefore attempts the normal plugin set again. Built-in Bundle failures and unattributed startup failures remain fatal so recovery cannot hide a product or profile-wide defect.

The desktop shell also injects one promise-returning plugin-management bridge at document start and accepts its messages only from the loopback main frame. The client package treats that bridge as a capability signal and otherwise registers nothing, so the normal browser surface is unchanged. In desktop mode it adds one `sidebar.footer.action` entry and one `shell.overlay` entry through existing additive slots; the sidebar owner remains untouched. The bridge lists only the Web profile's out-of-tree dependencies and treats GitHub's `dsh-plugin` topic and deepseek1024.com as separate, untrusted discovery indexes in a first-level Community discovery tab. Each catalog owns its search, pagination, and scroll state and prefetches its first page when the library opens. GitHub uses at most four concurrent structural inspections on the current page. The third-party source uses its paginated API, published category counts, and sort modes while native code keeps a short page cache. Topic repositories receive local structural classification directly. The third-party catalog contributes display metadata only; submission for review must parse a public npm target from the fixed site, pin an exact version through the npm registry, and then enter the same inspection. Native inspection classifies sources as a directly installable Profile Bundle, a package requiring an adapter, an external project, or a blocked source. It issues an install token only after an immutable exact npm version or Git commit has a valid root manifest, declares `dsh.bundle.patch`, and contains the referenced package-internal YAML composition entry. A published npm manifest that retains `workspace:` specifiers in runtime dependency fields adds one override risk per affected dependency. The client presents Force install and Cancel choices, while the native bridge requires `force: true` before consuming a risk-bearing token; cancellation revokes it. Force installation delegates the unchanged package to pnpm and may still fail rather than rewriting publisher metadata. Each token is otherwise single-use and expires after 15 minutes. Install and remove mutations delegate to the official plugin command while the visible runtime is stopped; installation forces exact saving and disables dependency lifecycle scripts. Review, success, and failure results append to a native JSONL audit log. This is a structural and immutable-source installation preflight, not a runtime sandbox, an endorsement by a third-party catalog or publisher, or a claim that arbitrary plugin code is safe.

The installed inventory projects the default `Deepseek-Files` and `@deepseek-ai/dsh-model-catalog` Bundles with exact package versions from their source manifests and marks them as non-removable through external dependency controls. The browser locale presents the latter as “Model Capabilities” or “模型能力目录”; pi-ai remains an implementation detail rather than a product label.

Source update fetches the configured checkout's `origin` branch declared by the application and prepares the target commit in a detached Git worktree. It installs the unchanged lockfile, builds the complete repository, starts the staged CLI against separate probe data, and requires both the CLI readiness line and an HTTP 200 response. The selected source pointer changes only after those checks pass. The previous pointer remains available for rollback, and the updater never resets or merges the active checkout.

A local application build records the developer checkout as its initial source. A distribution build instead deletes that path and embeds a compressed Git source snapshot assembled from tracked and non-ignored worktree files. First launch extracts the snapshot into Application Support before dependency installation and build, so the distributed application runs the packaged revision without carrying profiles, credentials, sessions, logs, ignored `.env` files, dependency caches, or the builder's home path. The extracted repository uses the distribution repository and branch declared in `Info.plist` for later detached-worktree updates. The DMG contains only this application and an Applications link; signing remains ad hoc until an operator supplies a distribution identity and notarization.

The desktop process binds no server of its own. It accepts the loopback URL produced by the child, keeps activated external links outside the embedded view, and sends SIGTERM before escalating to SIGKILL after the CLI's disposal allowance. The Harness file sandbox remains composed exactly as the Web profile defines it. The desktop executable does not enable macOS App Sandbox because spawning the runtime and accessing selected workspaces are required behavior.

## Alternatives considered

**Electron.** Electron would provide equivalent Web embedding and mature updater libraries, but it would add a second Node/Chromium distribution while the product already supplies a browser client. WKWebView keeps the custom shell small and uses the operating-system Web engine.

**Tauri.** Tauri also uses WKWebView on macOS and offers cross-platform packaging, but its command and permission layer adds a second application framework without removing the need to supervise a Node runtime. A dependency-free Swift shell is the narrower macOS implementation.

**Docker as the only runtime.** A container can strengthen filesystem and process isolation, but it makes workspace access a mount-management problem, depends on an external container engine, and conflicts with directly running a staged source worktree. Container execution remains a possible opt-in backend that must bind only to loopback, mount no Docker socket, and expose only selected workspaces and persistent data.

**Updating the active checkout in place.** Fast-forwarding and rebuilding the selected source uses less disk, but a failed build replaces the last working artifact and can collide with local development. Detached worktrees retain both source versions and make rollback a pointer change.

**Reusing one fixed loopback port.** A stable origin would preserve all browser storage without a bridge, but it gives desktop startup an avoidable port-collision failure and abandons operating-system port selection. Mirroring the one navigation cell keeps random ports and does not widen native ownership to arbitrary Web storage.

**Adding plugin controls directly to the sidebar owner or browser API.** Editing the sidebar would couple a desktop-only feature to shipped navigation chrome, while a browser Remote would expose package-manager mutation to every Web deployment. Existing additive footer and frame slots keep ownership separate, and the native main-frame bridge keeps the privileged operation desktop-only.

**Persistently disabling or uninstalling a plugin after one startup failure.** Either action would mutate user intent based on one process outcome and could turn a transient dependency or filesystem fault into a lasting configuration change. A one-run recovery profile keeps the normal profile authoritative while still making the desktop application usable.

## Consequences

The application retains full Web-profile behavior and native plugin installation without introducing a second client implementation. The plugin library can represent installed packages, review immutable sources, uninstall packages, and show audit records without pretending that one package-level switch controls Cordis entries contributed by that package. Plugins that require lifecycle scripts can fail after the safer installation path. A failing sideloaded Bundle can be absent for one recovered run, so its tools and UI are unavailable until a normal launch succeeds; all other profile state remains authoritative. A source update consumes disk for another checkout and dependency tree, and old worktrees remain until explicitly removed. The clean probe does not load the user's third-party plugins or prove compatibility with migrated persistent data, so a source switch can still fail for reasons outside one attributable side-loaded Bundle; source rollback remains available but cannot undo an upstream data migration.

The app is an ad-hoc-signed build that requires Node.js, Git, and first-build network access. The packaging step recreates the bundle before generating its icon and signature so stale resources cannot survive a rebuild. General distribution still requires bundling or installing a compatible Node runtime and applying the operator's distribution signing and notarization process. The built-in sandbox restricts file effects from composed agent tools; it does not turn third-party plugins into untrusted code, restrict their network access, or provide a whole-application container boundary.
