# Agent Note: 已归档会话设置页

Status: implemented

[English](2026-09-29-archived-sessions-settings-page.md) | 中文

## Problem

归档把会话移出导航但保留其记录，此前唯一能找回或彻底移除某个已归档会话的地方，就是当初执行归档的侧栏。批量归档过的用户没有可查阅的列表，无法搜索，也无法释放已不需要的会话所占的存储。归档集是注册表全局的，因此这个列表只能推导出来，而不能从某一处直接读出。

## Decision

`@deepseek-ai/dsh-client-ui-settings-archived-sessions` 以 id `archived-sessions`、order 40 注册一个 `settings.section` 条目，紧邻 `ui-settings-general` 的设置壳为该 id 预留的图标分支。本页自身不持有任何归档状态：它读取 `WorkspaceSnapshot` 和 `SessionListState`，并发出 `unarchiveSession` 与 `deleteSession`——与侧栏相同的命令，因此在这里的归档、恢复与删除就是侧栏的操作，而不是它们的第二套实现。

归档集是注册表全局的 `SessionId[]`，既无 `archivedAt` 也无按会话的标记，因此行的分组不能来自它。`deriveArchivedRows` 把它与会话列表的 `byId`（取标题和时间戳）以及 `WorkspaceView.sessionIds`（取分组）联结起来；被多个工作区持有的会话保留 Host 顺序中的第一个，这正是侧栏分组推导所解析出的同一归属。会话列表尚未描述的归档 id 会被跳过，而不是画成空行。

`SessionListState` 没有失败阶段，因此主机不可达时它停在 `pending`。`archivedReadStatus` 在两个来源都稳定之前报告 `pending`，使首次读取期间观察到的空归档不会被当成真的没有归档；跟随流中断的工作区是唯一的 `failed` 状态，本页不为它提供重试，因为重连由工作区控制器负责，且它没有发布任何能恢复终态流的操作。选中期间被删除的工作区，会在其选项消失的那次渲染上把视图收窄为未筛选列表。

行通过控制器自己的移除事件离开本页，而不是乐观移除，因此在跟随流尚未到达时该行仍然可见，而不是在宿主尚未接受变更之前就消失。

排序下拉提供更新时间、创建时间和标题。创建时间顺序只读摘要里的 `createdAt`，不读别的；测试夹具让两种顺序的首行落在不同的行上，因此读 `updatedAt` 的实现会失败而不是蒙混通过。客户端摘要的该字段之所以可选，是因为会话列表会自行构建一些行——宿主列表不携带的子代理——它们没有持久头部。缺失的创建时刻无法放到时间轴上，因此这样的行排在所有有时间的行之后，而不是自称纪元时刻，也不拿更新时间顶替；排序仍以另外两种顺序同样的时间和会话 id 决胜保持全序。每种顺序只通过一次查表同时命名下拉行和触发按钮的当前值，两者因此不会说法不一。

一行的两个命令在悬停和键盘聚焦时淡入，且只在 `@media (hover: hover)` 之内淡入，别处一律不淡入，因为触屏设备永远不会触发本该显示它们的悬停。`@media (max-width: 560px)` 的规则把行排成两行——标题在第一行，日期与命令在第二行——因为在触屏上让命令常驻可见，会使单行放不下三者。两个下拉触发器采用 `Input` 组件的尺寸框，使工具栏读起来是一排控件；页面框架是官方设置页的那个。本页样式表中没有任何规则声明字面颜色或 `font-family`，全部使用共享 token。

批量删除作用于当前视图——工作区筛选和搜索词决定其覆盖哪些会话——但在第一个对话框打开时就把该视图冻结成一份由会话 id、数量与名称构成的 `DeleteArchivedScope`，本次运行删除的正是这些 id。第一个对话框说明该范围和数量，第二个 `RiskConfirmation` 要求确认，两个步骤上显示的数量与本次运行访问的集合是同一批会话，因此两个步骤之间的筛选变化或流更新无法扩大已确认的删除。对话框每次删除挂载一次而不是切换开关，因此每次打开都从范围步骤开始且确认复选框未勾选。

两条删除路径遵守同样的规则：宿主接受的删除关闭其对话框，拒绝的删除保留对话框并清空确认复选框，已经发出的命令则保持对话框打开且无法关闭，因为关掉对话框只会把仍在进行的工作藏起来。`RiskConfirmation` 的 `cancelDisabled` 是最后这条规则的唯一机制——取消按钮、关闭按钮、页面遮罩与 Escape 都走同一个关闭守卫。删除逐条执行；部分失败的运行会报告成功数与失败数，且不重试。

## Alternatives considered

**页面自持归档缓存。**归档状态的第二份副本会与注册表漂移，使侧栏与本页对同一批会话的说法不一致。页面改为每次读取时从两个快照推导自己的行。

**删除归档中的全部会话。**截图中的控件读起来像全量删除，但归档是注册表全局的，其规模在动手之前并不可见。把本次运行限定在当前筛选，并在第一个对话框里说明该范围，使用户确认的数量与其确认的效果是同一个数。

**在确认时重新读取可见行。**运行开始时再次投影筛选，会让两个对话框之间发生的一次筛选变化，或一次归档并被流更新列出的新会话，把第一次确认从未展示过的行加入删除范围。在说明范围时冻结这些 id，使被确认的集合就是被删除的集合，代价是一次运行会漏掉对话框打开之后才出现的行。

**命令 resolve 后立即移除行。**移除行的事件由控制器发布；乐观移除会在宿主尚未真正删除之前就藏起一个会话，这对一个破坏性页面而言是错误的方向。

**把主机不可达报告为失败。**会话列表无法区分主机不可达与首次读取进行中，因此 `pending` 才是诚实状态，而工作区流是唯一能报告 `failed` 的来源。

**拿更新时间给本地构建的行补上创建时间。**这样它仍能落在时间轴的某个位置，排序也只需一次数字比较，代价是把子代理归档到它最近一次运行的时刻——本页本来就在展示这个事实，而读创建时间顺序的人会误当成对话开始的时间。该行没有创建时刻，因此它排在最后，也不对自己何时开始作任何声明。

**把缺失的创建时刻当作纪元。**列表仍能排定，但本地构建的行会以归档中最古老之物的身份领跑创建时间顺序，这和拿更新时间顶替一样不实，只是更难被发现。

## Consequences

本页不增加平行状态，也不增加第二条命令路径，因此从这里发起的恢复或删除会通过同样的事件对侧栏和每个其他工作区订阅者可见。`archived-view.ts` 中的投影是纯函数，因此本页的列表行为——联结、归属、筛选、排序、分组与读取状态——无需宿主即可测试。

每种顺序的全序都以会话 id 兜底，而该 id 是计数器而非时间，因此两个会话可以标题相同、时间戳相同，却仍能确定地排定先后。创建时间顺序把会话列表自行构建的行留在末尾，因此想看最新对话的人不会在那里遇到一个子代理。批量运行不可续跑：部分失败会报告数量并让剩余会话保持归档，需要重新打开对话框。无法取消的运行同样无法中止，而工作区流断开后列表会一直隐藏，直到工作区控制器重连为止。

该页仅存在于浏览器侧，不注册任何模型面，因此不改变任何请求、会话事件或快照输出。聚焦的组件测试与投影测试是它的验收证据；无密钥的录制定时会话快照重放的是模型可见流量，无法表示控制面的归档操作。
